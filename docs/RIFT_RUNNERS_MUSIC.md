# Neon Wake — music update to Checkpoint 02

**Browser version:** 0.1.1. **Date:** 2026-09-15. This is a focused music update,
not the larger Checkpoint 03 integration/deployment milestone delegated to Claude.
The original native C++ game and camera/inference implementation are unchanged.
Nothing was pushed or deployed during this update.

## Sound and controls

An original 116 BPM synthwave score is now generated by Web Audio in the browser.
The same chord progression links the arrangements: warm stereo pads and sparse
arpeggios in the hangar, bass and drums during flight, and extra hats/sparkles while
boosting. The melody varies over a 32-bar form. Countdown adds a restrained pulse;
results return to a calmer arrangement. These are arrangements of one theme, not
three licensed songs or downloaded recordings.

Click **SOUND ON** to enable music and effects. **M** toggles the master mute,
except while typing/adjusting an input. **MIX** opens the sound mixer. Music and
sound effects have independent sliders; setting either to zero mutes that channel.
Default levels are music 48%, effects 65%. Only volume preferences are saved locally;
every newly loaded page begins with sound off, even if the previous visit used audio.
Storage denial or malformed settings fall back safely. No AudioContext is created
on page arrival or merely opening the mixer.

Pausing stops the scheduler and suspends audio. Opening MIX during flight safely
pauses the ship and previews the hangar arrangement; closing MIX leaves the flight
paused until the player explicitly resumes. Hidden tabs/pagehide release scheduled
voices and suspend the audio context. Returning to an already opted-in menu/result
can resume its music; a hidden in-flight game stays paused. This never resumes or
requests a webcam. Camera consent and stop controls are unchanged.

## Implementation

- `src/music.js`: deterministic score, tempo and bounded Web Audio synth voices.
  Pad, bass, lead, pluck, kick, snare, hats and boost sparkle are synthesized; the
  drum noise buffer is generated deterministically, not loaded from a sample file.
- `src/audio.js`: lazy, opt-in audio lifecycle, separate gain buses, compressor,
  25 ms lookahead scheduler, user levels and original game effects. A maximum of
  four steps is scheduled per tick; a long stall skips missing notes instead of
  dumping a backlog. Music voice count is bounded at 96, effect voices at 32.
  The AudioContext clock sets note timing, not the rendering frame rate.
- `src/app.js`, `index.html`, `styles.css`: state/intensity integration, accessible
  labelled sliders, mixer dialog and M hotkey. Read-only diagnostics include audio
  state, levels, scheduler state and active voice count; no camera data is exposed.
- `tests/audio.test.mjs`: 23 new tests; the existing 57 unit tests are retained.
- `tests/browser_smoke.py`: four audio scenarios added to the nine existing cases.
  Audio tests use real Web Audio; camera/inference tests remain synthetic.
  Driver-side polling avoids the in-page string-eval wait that conflicted with CSP
  in a standalone-preview test; it does not change the shipped application's CSP.
- `tools/render-music-preview.py`: developer-only offline rendering with the same
  score and instruments. It needs Playwright/Chromium, not a runtime game dependency.

No music-service integration, microphone access, analytics, external music URLs or
new runtime dependencies were added. Music has no network requirement. This does
**not** change the separately disclosed remote MediaPipe/model requests in camera
mode, and is not a vendor audit of that pre-existing hand-tracking dependency.

## Reproduction

From `rift-runners/`:

```sh
npm run check
npm test
npm run serve
# Open http://localhost:8080/driftfall/ and click SOUND ON, then MIX.
```

Browser dependencies remain in `tests/requirements.txt`. With the game served on
port 4173, these are the normal-hosting validation commands for Claude:

```sh
python tests/browser_smoke.py --out qa-webgl
python tests/browser_smoke.py --compatibility --out qa-compatibility
python tests/browser_smoke.py --audio-only --out qa-audio
python tools/render-music-preview.py --out qa-music-preview
```

The Pages workflow already copies all of `src/`; it includes `music.js` without a
new asset-copy rule. Its normal HTTP browser tests now include the audio scenarios.
No GitHub workflow run or live deployment was performed here.

## Executed validation and limits

| Check | Observed result |
| --- | --- |
| Syntax/initial HTML | Passed, 10 JavaScript modules |
| Node tests | 80 passed: 57 prior + 23 audio/score tests |
| Browser regression | 13 passed: 9 prior + 4 audio scenarios |
| Real-time audio graph | Non-silent samples measured using a real Chromium AudioContext/analyser |
| Local HTTP assets | 28 byte/MIME checks plus 2 expected 404s passed, at root and `/driftfall/` |
| Offline soundtrack render | 37.49 seconds, stereo 44.1 kHz, 492 scheduled notes, no non-finite/clipped frames |
| Standalone music preview | Opt-in, real audio start, boost selection, volume and mute passed; no network requests |

The offline preview's absolute peak was 0.376 at the default mix. Hangar RMS was
0.0297 and flight RMS 0.0386. These are digital measurements of this sample, not a
physical loudness, speaker quality, hearing-safety or long-session performance claim.
The final preview fades out; the in-game score continues until muted/paused.
For one-time offline rendering only, the queued-voice cap is raised because all
future notes must be scheduled before rendering; the live game cap is unchanged.

**Browser limitation:** normal navigation to the local server was attempted and
returned `ERR_BLOCKED_BY_ADMINISTRATOR`. The game regression therefore used the
existing documented `--memory --compatibility` harness (Canvas2D; shipped sources
loaded as blobs; CSP removed only in that game-test document). Real Web Audio was
available and was not mocked. The standalone inline preview kept its own CSP, but
was also loaded in memory, not through `file://` or HTTP. No environment policy was
changed. The test report must not be represented as deployed-browser validation.

Still pending: ordinary HTTP/production CSP/module loading, WebGL rendering,
physical webcam/model tests, Safari/Firefox/iOS audio behavior, physical speaker or
headphone listening, tracking-plus-audio latency/thermal tests, GitHub Actions and
Pages deployment. No new multiplayer capability is claimed.
